# Design Philosophy

> 这套技能背后的设计理念。
> 仿照 superpowers 的"理念 > 工具"原则,把方法论写下来,让用户和 agent 都能对齐。

## 核心原则

### 1. 流程 > 临时发挥

游戏开发诱惑太多,容易"灵感来了直接写"。
我们强制让流程节点明确,**每个节点有可识别的产物**。

| 节点 | 产物 |
|------|------|
| 想法 | 概念包 |
| 设计 | GDD |
| 验证 | 原型 |
| 计划 | plans/*.md |
| 实现 | 代码 + 测试 |
| 审查 | reviews/*.md |
| 收尾 | git tag + changelog |
| 发布 | build/* |

### 2. 分层测试 > 单一 TDD

游戏代码不是单一形态:
- 算法/数据 = 严格 TDD(逻辑层)
- 多节点组合 = 集成测试(装配层)
- 手感/视觉 = 手动 + 录制(体验层)

**不要让逻辑层的 TDD 蔓延到体验层**。写 UI 单测是负担,手动跑过去是高效。

### 3. 数据驱动 > 硬编码

2D 游戏的关卡/敌人/道具**都是数据**,不是代码。
用 `Resource` 把数据抽出来:
- 改难度不动代码
- 关卡可独立保存为 `.tres`
- 程序生成(Roguelike)成为可能

### 4. 纯函数 > 副作用函数

物理/AI 逻辑里**能抽成纯函数的全抽**。
`compute_motion(prev_velocity, input, dt) -> new_velocity`
不依赖节点、不调引擎 API,直接 GUT 测。

### 5. 准强制型调度

不是 superpowers 那种"必须"的强约束(个人项目太重),也不是完全自由(等于没流程)。
- 关键节点:**必须**(测、审、收尾、发布)
- 路径选择:**建议**(prototype 选做、scope fence 自由)
- 默认 vs 显式:有合理默认,但允许用户显式覆盖并记录

### 6. 自包含

一个 `git clone` 就能用:
- 不用装额外 CLI(除了 Godot)
- 不用订阅服务
- 不用网络(运行时不联网)
- 样例项目内嵌,看完就能复制改造

### 7. 个人而非团队

- 不强制 code review
- 不强制分支策略
- 不强制 CI
- 不强制文档

但**所有"团队级"功能都给出推荐配置**,需要时启用。

## 哲学与 superpowers 的差异

| 维度 | superpowers | 本套件 |
|------|-------------|--------|
| 严格度 | 强制 | 准强制 |
| 测试 | 全栈 TDD | 分层(逻辑/装配/体验) |
| 调度入口 | using-superpowers | using-game-dev |
| 知识库 | 无(纯工作流) | 7 个 Godot 知识技能 |
| 资产 | 不涉及 | asset-pipeline |
| 关卡 | 不涉及 | level-data-flow |
| 发布 | 不涉及 | release-checklist-2d |
| 目标 | 任何软件 | 2D Godot 游戏 |

## 何时不要用本套件

- ❌ 3D 项目(等 godot-3d-superpowers)
- ❌ 一次性原型 / Game jam 48h(流程太重,直接干)
- ❌ 商业化大型项目(需要更专业的 CI/QA/版本管理)
- ❌ 完全不想被约束的个人项目(用裸 Godot 就行)

## 演进规则

1. 模式性问题(反复出现同一反模式)→ 升级到对应 skill
2. 错过新 Godot 4.x 特性 → 升级 godot-docs-4-7
3. 流程太重/太轻 → 调整准强制级别
4. 用户明确说"跳过 X 多次" → 考虑把 X 改成"建议"
5. 用户明确说"加严 X" → 把 X 升级到"必须"

不要为了"完整"而保留不再有用的检查点。**用进废退**。
